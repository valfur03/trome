# Code structure of the server

These rules are for every change and every review of the server (`server/`) and of the shared test files (`contracts/`), and for every run of a server command.

decision-6 (sections 2, 3 and 6) and decision-40 explain these rules.
The reviewer checks them, as for the iOS app.

- **Two modules, one direction.** `server/src/core/` holds the logic in plain TypeScript: the routes, the rules, the counts, the logs.
  `server/src/cloudflare/` is the thin layer on the Cloudflare API: the Worker entry (`worker.ts`, the composition root), the Durable Object, and the adapters (for example `DurableObjectSqlDatabase`).
  `cloudflare/` depends on `core/`, never the reverse.
  Why: decision-40 keeps the exit to another host a medium task, not a rewrite.
- **`core/` runs on Node too.** It imports no `cloudflare:` or `node:` module and no file of `cloudflare/` (ESLint fails on it), and it type-checks with the types of Node and none of Cloudflare (`test/core/tsconfig.json`).
  Its unit tests run on Node (`test/core/`), with a real SQLite database (`node:sqlite`) behind the `SqlDatabase` interface.
  A platform service gets a small interface in `core/` and an adapter in `cloudflare/`.
- **Tests.** `server/test/core/<feature>/<file>.test.ts` (Vitest on Node, with a fake clock) for the logic.
  The examples of the app API in `contracts/api/` are checked by `server/test/core/http/departures-contract.test.ts`.
  `server/test/cloudflare/<file>.test.ts` (Vitest in the Cloudflare runtime, `@cloudflare/vitest-plugin`) for the thin layer: the Worker, the Durable Object and its storage.
  Tests of the scripts: `server/scripts/tests/<name>-test.sh`.
  The server tests read the recorded PRIM answers of `contracts/prim/` (no copy).
  No real PRIM call and no real secret in a test: `fetch` to PRIM is faked with the recorded answers.
- **The server changes by adding.** Every build that riders may hold has a recorded set of promises in `contracts/builds/<set>/`: what it sends, how it reads each answer, how long it waits (decision-93, decision-94).
  `make server-check` judges the server against every set (`server/test/cloudflare/build-promises.test.ts`), and fails when a recorded file changes or goes while a build of its set is in the field (`server/scripts/build-promises-check.ts`).
  Never edit, move or delete a recorded set to make the check pass, and never change the app code together with the server to get round it: add the new path, header or field next to the old one, which only new builds read.
  A set leaves only when the table "The builds that riders may hold" of the release guide retires all its builds, with a reason; a server change is never that reason.
  Why: a build in the field never changes, so a record that a server change could edit to match itself would protect no rider; editing the example to match the server was the careless fix that let every break through (TASK-400).
  A new situation of a set gets its scenario in `build-promises.test.ts` (in `start-promises.ts` for the start of the Live Activity); the matchers of `build-promises.ts` only grow.
- **Folders by feature** inside `core/` (`http/`, `logging/`, `config/`, `storage/`, `time/`, `auth/`, `relay/`, `budget/`, `usage/`), with the same names in `test/core/`.
  The fakes of the tests go in the folder of what they replace (`test/core/time/fake-clock.ts`, `test/core/relay/fake-prim-client.ts`).
  Files in kebab case, one main export each.
- **Secrets by name only.** The PRIM key, the app token and the owner token are Cloudflare secrets (`secrets.required` in `server/wrangler.jsonc`).
  Their values are never in git, never in a log line (the logger of `core/logging/` hides them, and a unit test proves it), and never in the app.
  `server/worker-configuration.d.ts` is generated by `wrangler types` and in git: after a change of `server/wrangler.jsonc`, run `npm run types` in `server/` (`make server-check` fails when it is old).

## The server and its commands

`server/README.md` explains the server and its commands; `server/guide/how-it-works.md` its API and its quota, and `server/guide/deploy.md` the deploy and the secrets.

- **Node 24.** Run the server commands through fnm, which reads `.nvmrc`: `fnm exec --using=.nvmrc -- make server-check`.
  Never run `fnm use`: it changes the Node of the prompter's terminal.
  The same goes for `make check` when your task changes `server/`, `contracts/` or the station list of the app (`stations.json` of `TROMECore`, which the server bundles): `make check` runs `make server-check` only then, so the app tasks never install `server/node_modules` (about 300 MB).
- **Use your own port.** `make server-dev` uses 8787 in the main folder only (the prompter's), 8787 plus the number at the end of the folder name in a worktree (8974 in `task-187`), and a port from 9800 to 9899 in a worktree whose name ends with no number (for example `qa`).
  Run it in the background, and stop it with `make server-stop` as soon as your check is done, and before your job ends.
- **Fake secrets only.** `make server-dev` creates `server/.dev.vars` (ignored by git) from `server/.dev.vars.example`, with fake values.
  Never put a real key in it, and never commit it (`make server-check` fails when git tracks a `.dev.vars` or `.env` file of `server/`, or when such a file is new and git does not ignore it).
- **No deploy and no account** (a rule of `CLAUDE.md`).
  The workflow `.github/workflows/server-deploy.yml` deploys `server/` from `main` to the staging Worker: `make server-check`, then the deploy, then a check that staging answers (`server/guide/deploy.md`).
  The production Worker is still deployed only by the prompter, with `make server-deploy`.
  In a run, wrangler answers its own questions "yes": the run passes `--strict` to `wrangler deploy`, and a workflow step never calls a wrangler command that can ask one (`rollback`, `delete`, `secret put` or `secret delete`).
  Never give the Cloudflare token or the app token to a step that installs packages or runs tests (`.claude/rules/github.md`).
- **`make release-server-check`, `make release-server-timing` and `make release-tokens-check` are the prompter's.** They read the real app tokens of `ios/Config/Server.xcconfig` or `ios/Config/BuildTokens.txt` and call the production server; the timing makes up to 2 PRIM calls, the tokens check one per build in the field.
  An agent never runs them in the main folder; in a worktree, which has no such file, they only say that the file is missing.
  Check a change of them with `ios/scripts/tests/release-server-check-test.sh`, `release-server-timing-test.sh` and `release-tokens-check-test.sh`, which use a fake server and fake files.
- **No PRIM call from `make server-dev`.** The dev server calls the real PRIM, with the fake key, as soon as a departures request has the right app token.
  So an agent never sends `GET /v1/stops/.../departures` with the app token of `server/.dev.vars` to it: check those answers in the tests, which fake PRIM.
  Requests that never reach PRIM are fine (`/health`, a missing or wrong token, a bad stop reference, `make server-counts` with the fake owner token).
- **Server jobs need no Simulator and no lock.**
